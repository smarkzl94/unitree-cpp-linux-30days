# 一、Linux：优先级与资源上限

操作系统不会让一个进程无限吃 CPU、无限开文件。今天的 `nice` / `ulimit` 就是在说：**资源是有界的**。对照 C++：有界队列满了，生产者必须停下来等，而不是无限 `push` 把内存撑爆。

## 1. `nice`：启动时的「谦让程度」

Linux 里用户能调的调度优先级常叫 **nice**。数值越大越「客气」，越不容易抢到 CPU。

```bash
nice -n 10 ./your_mpmc          # 以 nice=10 启动（比默认更客气）
nice -n -5 ./your_mpmc          # 更急（通常要权限，普通用户常失败）
```

常见范围：**-20（最急）到 19（最客气）**。默认一般是 0。

注意：nice **不是**实时优先级。机器人硬实时用另一套（`SCHED_FIFO` 等），今天只建立「谁更客气」的直觉。普通学习机上把 nice 调高，程序可能跑得更慢、更容易被别的任务抢走 CPU——用来体会「调度在干活」，不要用来压垮系统。

## 2. `renice`：已经在跑的进程改优先级

```bash
ps aux | grep your_mpmc
renice -n 15 -p PID             # 把该 PID 的 nice 改成 15
```

`nice` 管启动，`renice` 管中途改。改别人的进程通常要权限；先改**自己的**测试程序。

`top` 里有 NI 列，改完刷新应能看到变化。线程默认继承进程的 nice（细节实现相关，预习记住「先观察自己的进程」）。

## 3. `ulimit`：当前 shell 的资源天花板

```bash
ulimit -a                       # 看所有限制
ulimit -n                       # 最多能开多少文件描述符
ulimit -u                       # 最多多少用户进程（含线程，视实现）
ulimit -s                       # 栈大小（常 KB）
```

队列、socket、日志文件都占 fd。线程要栈。无界增长最后会撞上这些墙，表现为 `push`/`open`/`std::thread` 失败，而不是「再买点内存就好」。

```bash
ulimit -n 256                   # 仅对当前 shell 及它拉起的进程生效
```

不要把硬限制乱改成无限再去开几万线程。今天目标是：**看见上限，理解有界。**

## 4. 和有界队列的同一句话

| 系统 | 满了怎么办 |
|------|------------|
| `ulimit -n` | 再 `open` 失败 |
| 有界队列 | 生产者阻塞（今天策略）或丢弃（要写清） |
| 无界 `queue` | 内存涨到 OOM |

Day09 选**阻塞、不丢**：满了生产者 `wait`，消费者 `pop` 后 `notify` 生产者。和内核「资源不够就阻塞/失败」是同一类设计。

## Linux 口述（预习时自己答）

1. `nice` 数值越大越怎样？  
   越客气，越不容易抢 CPU。-20 最急，19 最客气。
2. `nice` 和 `renice` 差在哪？  
   `nice` 启动时带优先级；`renice` 改已经在跑的 PID。
3. `ulimit -a` 看什么？和队列有何类比？  
   当前 shell 的资源上限（fd、栈、进程数等）。有界队列满了要有策略，不能假想无限。

# 二、C++：MPMC 有界队列，证明不丢

## 为什么昨天的单产单消不够

真实系统常是**多传感器 + 多消费者**（或多模块同时入队）。同一把锁护队列在正确性上仍然够用，但要验证三件事：

1. **不丢、不重**：每个序号恰好被消费一次。
2. **有界**：容量满时生产者阻塞，而不是无限涨。
3. **能结束**：生产完、消费完、所有线程 `join`，`shutdown` 不挂死。

## 1. 同一把锁：正确，但可能是瓶颈

所有 `push`/`pop` 抢同一 `mutex`。逻辑简单，面试先把这个写对。吞吐不够时才考虑分片、无锁——Day11 会说无锁更难写对，今天不要提前优化。

生产者不只一个：两个 `push` 不能同时改 `std::queue`。消费者同理。条件变量仍用：

- 空 → 消费者 `while (q.empty() && !shutdown) cv.wait`
- 满 → 生产者 `while (q.size() >= cap && !shutdown) cv.wait`

可以用一把 cv，`notify_all`（空和满两类等待者都可能要醒）；也可以空/满两把 cv，`notify_one` 更精确。预习先会**一把 cv + notify_all**，正确优先。

## 2. 有界 + 不丢：满时阻塞，不覆盖

```cpp
void push(T x) {
    std::unique_lock<std::mutex> lk(m_);
    while (q_.size() >= cap_ && !shutdown_) cv_.wait(lk);
    if (shutdown_) return;
    q_.push(std::move(x));
    cv_.notify_all();
}
```

和 RingBuffer「满了覆盖最旧」不同：指令/任务队列通常**不能丢**。今天策略写死：**阻塞等待空位**。覆盖是遥测的策略，留给 Day12。

无界队列：实现简单，内存无上限，长时间生产者快于消费者会把机器拖死。有界把背压传回生产者——和 `ulimit` 同一直觉。

## 3. 用序号证明完整性

生产 N 个任务，任务带 `id = 0 .. N-1`（或多个生产者划分区间，或原子 `fetch_add` 发号）。

消费端：

- 每个 id 插入 `std::set` 或 `vector<char> seen`（**set 本身要锁或仅线程本地再合并**）。
- 结束时：`seen.size() == N`，且没有空洞、没有重复。

```cpp
// 主线程汇总（工人先 join）
assert(seen.size() == static_cast<size_t>(N));
for (int i = 0; i < N; ++i) assert(seen.count(i));
```

校验逻辑若多线程同时改同一个 `set` 而无锁，校验本身就有数据竞争——「证明」作废。做法：每个消费者本地容器，join 后主线程合并；或一把专门的结果锁。

## 4. 线程生命周期

```text
启动 workers → 生产 N 个 → 生产者 join
→ shutdown（若消费者可能空等）→ 消费者把剩余 pop 完并退出 → 消费者 join
→ 再析构队列
```

易错：主线程先毁掉 queue，工人还在 `wait`。或只 `join` 生产者，消费者仍堵在空队列上。生产结束要让消费者知道「不会再有新任务」：`shutdown` 或额外的「完成计数」。

异常路径同样要能退出：某工人抛错也不能让别人永等。预习用 RAII/`join` 在正常路径先做对。

## 5. 易错点（看懂再上机）

1. **无界当有界**：测了几条就说正确，没把容量压满。
2. **校验 set 有竞争**：多消费者同时 `insert` 无保护。
3. **只测幸福路径**：不测「生产结束、队列空、消费者在 wait」。
4. **`notify_one` 叫醒了错误的一侧**：满等的生产者被一个 pop 叫醒还好；若空等和满等混用一把 cv，`notify_one` 可能叫醒同类，用 `notify_all` 更稳。
5. **先析构再 join**。

## C++ 面试口述（预习时自己答一遍）

1. **如何证明没有丢任务、没有重复消费？**  
   全局唯一序号；消费记录集合；join 后检查大小为 N 且 0..N-1 齐全。记录结构本身要无竞争。

2. **有界和无界怎么选？**  
   不能丢的任务用有界+阻塞（背压）。遥测可覆盖。无界只适合能保证消费者跟得上、或任务数有外部上限。

3. **MPMC 为什么还用一把锁就够（正确性）？**  
   队列不变量由这一把锁串行化。慢可以以后再优化，先正确。
