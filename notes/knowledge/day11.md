# 一、Linux：`lscpu` 与缓存行

线程不是跑在抽象真空里，而是跑在 **CPU 核**上。核与核通过**缓存**交换数据。缓存按固定大小的块传输，这块叫 **cache line（缓存行）**，x86 上常见 **64 字节**。两个变量只要落在同一行里，一个核改其中之一，另一个核的那一行常常要作废再取——即使你逻辑上「各改各的」。

## 1. `lscpu`：先看本机长什么样

```bash
lscpu
```

先认：

- **CPU(s)**：逻辑 CPU 数（超线程会让它大于物理核）。
- **Core(s) per socket / Socket(s)**：物理核与插座。
- **Thread(s) per core**：1 或 2（超线程）。
- **L1d/L1i/L2/L3**：各级缓存大小。越小越靠近核、越快。

```bash
getconf LEVEL1_DCACHE_LINESIZE    # 数据缓存行大小，常见 64
lscpu | grep -i cache
```

笔记写下：逻辑 CPU 数、L3 大小、缓存行字节数。Day06 看过 `/proc/cpuinfo`；`lscpu` 是同一信息的摘要版。

## 2. 缓存行：为什么「乱共享会慢」

CPU 不以「一个 int」为单位同步，而以一整行（如 64B）为单位。

```text
同一缓存行：  [ counter_A (8B) | counter_B (8B) | ... 凑满 64B ... ]
```

线程 A 只 `++counter_A`，线程 B 只 `++counter_B`。逻辑无数据竞争（若都是 atomic 或已分区），但硬件仍把这一行在两核的缓存之间来回作废——这就是后面 C++ 要说的**伪共享（false sharing）**。

真共享：两核就是在改同一个变量（需要同步，慢有理由）。  
伪共享：变量不同，只是凑巧邻居，慢得「冤枉」。

## 3. 和并发程序的关系

`top -H` 看到两线程 CPU 都很高，但吞吐上不去，有时就是伪共享或锁争用。今天先建立模型：

- 核多 ≠ 线性加速。
- 共享的最小硬件单位是缓存行，不是 C++ 变量。
- 对齐、填充（padding）可以把两个热点计数拆到不同行（了解即可，上机对比时能说这句话）。

## Linux 口述（预习时自己答）

1. `lscpu` 重点看什么？  
   逻辑 CPU 数、核/插座、各级 cache；缓存行大小常用 `getconf LEVEL1_DCACHE_LINESIZE`。
2. 缓存行是什么？常见多大？  
   CPU 与内存/核间同步的块；x86 上常 64 字节。
3. 为什么两个无关计数器也会互相拖慢？  
   落在同一缓存行时，一行只能「属于」一方缓存，来回失效——伪共享。

# 二、C++：`atomic`、内存序入门、伪共享

## 为什么需要 atomic

`int x; x++` 在多线程里不是原子的：读-加-写三步可交错，结果丢失更新。`mutex` 能修，但对**一个计数器、一个退出标志**往往太重。`std::atomic<T>` 保证这一次操作完整，且定义好转圈可见性。

**无锁 ≠ 更快，更 ≠ 更容易正确。** 复杂不变量（队列头尾、满空）仍用 mutex（Day08/09）。今天边界：计数、标志、简单状态。

## 1. `std::atomic<T>` 常用操作

```cpp
#include <atomic>

std::atomic<int> n{0};
n.fetch_add(1);          // 原子 ++，返回旧值
n.load();                // 读
n.store(0);              // 写
++n;                     // 等价于 fetch_add(1)，默认顺序最严
```

适用：开关、统计、状态枚举（值足够简单、不依赖「两个字段同时变」）。

不适用：`atomic<MyBigStruct>` 若 T 太大，实现可能内部仍加锁；非平凡对象不要乱 atomic。更常见的错是：**拆成两个 atomic 却当一笔事务**——`a.store(1); b.store(2);` 中间别人能看见 1 和旧 b。

## 2. `memory_order`：先会默认，再认名字

每个 load/store 可带内存序。默认 **`memory_order_seq_cst`（顺序一致性）**：所有线程看见的原子操作有一个总序，最好理解，也最严，略慢。

预习认这几个（先会用默认写对）：

| 序 | 直觉 |
|----|------|
| `seq_cst` | 最严，默认。计数器、标志用它就够。 |
| `relaxed` | 只保证本操作原子，几乎不约束周围读写顺序。统计「大概次数」有人用；同步算法很容易写错。 |
| `acquire` | 读：之后的读写不能重排到这次读之前。常配 release。 |
| `release` | 写：之前的读写不能重排到这次写之后。发布数据时用。 |

```cpp
flag.store(true, std::memory_order_release);
if (flag.load(std::memory_order_acquire)) {
    // 能看见 release 之前对普通变量的写入（在正确配对时）
}
```

**松散序难写对。** 岗上先 `seq_cst`。面试能说：「默认最严；relaxed 只原子不计顺序；acquire/release 成对做发布-订阅。」不要假装会手写 Dekker。

## 3. `volatile` 不能替代 `atomic`

`volatile` 告诉编译器「每次都真的读内存」，用于寄存器映射等，**不保证**多核原子性，也不提供 acquire/release。并发计数用 `atomic`。两者叠在一起也不等于「更安全」。

## 4. 伪共享（概念必须会说）

```cpp
struct Counters {
    std::atomic<int> a{0};
    std::atomic<int> b{0};  // 紧挨着，常在同一 64B 行里
};
```

两线程分别 `fetch_add` a 和 b：无数据竞争，但缓存行来回踢，可能比「各用带 padding 的结构」慢很多。

缓解（了解）：`alignas(64)` 让 b 另起一行；或每个线程写私有计数，最后再汇总（Day09 校验用本地 set 同一思路）。

Day06 RingBuffer 的读写游标若挤在一行，单产单消也会被伪共享咬一口——同一概念。

## 5. 何时不该上无锁

- 要同时维护多个字段的不变量（队列 size 与头尾）。
- 需要等条件（空/满）——还是 CV + mutex。
- 团队要能 gdb 看懂。无锁 bug 往往是「偶现、无数据竞争报告、逻辑错」。
- 没测过热点就改无锁：过早优化。

上机：同一套 `++`，有锁 vs `atomic`，比正确性和粗略耗时即可，不要为了快去上 `relaxed`。

## 6. 易错点（看懂再上机）

1. 两个 `atomic` 当事务。
2. 用 `volatile int` 当退出标志。
3. 对 `std::string` 之类乱包 atomic。
4. 把「无锁」当成性能保证。
5. ABA：无锁链表里节点被复用导致指针看起来没变（今天只记名词，队列仍用锁）。

## C++ 面试口述（预习时自己答一遍）

1. **什么时候不该上无锁？**  
   多字段不变量、需要等待、正确性重于那点计数开销、还没证明锁是瓶颈。

2. **`volatile` 能替代 `atomic` 吗？**  
   不能。用途不同：volatile 防编译器优化；atomic 才是并发原子与可见性。

3. **什么是伪共享？**  
   不同核改不同变量，但它们在同一缓存行，缓存一致性协议让行来回失效，性能掉。
