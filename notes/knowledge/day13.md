# 一、Linux：重定向与 `tail -f`

传感器/控制一跑就是很多秒，指标若只打在滚动终端上，很难回头对比。标准做法：stdout/stderr 进文件，另一个终端 `tail -f` 看最新几行。日志太勤会**扭曲**你要测的延迟（写盘本身很慢），所以先会重定向，再克制打印频率。

## 1. 重定向：`>` `>>` `2>` `2>&1`

```bash
./control_demo > run.log                 # stdout 进文件（覆盖）
./control_demo >> run.log                # 追加
./control_demo 2> err.log                # 只有 stderr
./control_demo > run.log 2>&1            # stdout+stderr 都进 run.log
./control_demo > run.log 2> err.log      # 分开
```

- `>`：从空文件开始写，旧内容丢掉。
- `>>`：接到文件末尾，适合多次实验。
- `2>`：文件描述符 2 是 stderr；`2>&1` 表示 stderr 跟 stdout 走同一个地方。

Day03 管道是「接到另一个命令」；今天是「接到文件」。编译信息在 stderr，只重定向 `>` 时错误仍在屏幕——排错时记住看 `2>`。

```bash
./control_demo > run.log 2>&1
# 另开终端：
tail -f run.log
```

## 2. `tail -f`：盯文件增长

```bash
tail run.log           # 默认最后 10 行
tail -n 50 run.log     # 最后 50 行
tail -f run.log        # follow：一直显示新追加的行，Ctrl+C 停
```

`-f` 不重新打开逻辑上的「整份历史」，而是等新内容。程序若是块缓冲，文件里可能一时没有你刚 `cout` 的行：测试指标可 `std::endl` 或 `std::flush`，或启动前：

```bash
stdbuf -oL ./control_demo > run.log 2>&1
```

行缓冲后 `tail -f` 才跟得上。不要每帧 flush 一次（又回到「日志扭曲测量」）。

## 3. 和测量的关系

- **运行日志**：偶尔打印 `mean_latency_us`、`drop`、`p99`，例如每秒一行。
- **原始每帧日志**：调试用，测延迟时关掉。
- 文件比终端稳定：你可以实验结束后 `grep drop run.log`。

`tail -f` 只读观察，不改变程序；程序仍要自己把数字写到 stdout。

## Linux 口述（预习时自己答）

1. `>` 和 `>>` 差在哪？`2>&1` 是什么？  
   `>` 覆盖，`>>` 追加。`2>&1` 让 stderr 与 stdout 同一目标。
2. `tail -f` 干什么？  
   持续显示文件末尾新增内容，适合看长跑程序。
3. 为什么测延迟时不能每帧打日志？  
   写文件/终端很慢，会改变调度和延迟，测到的是「打日志的系统」不是控制循环。

# 二、C++：控制消费者与延迟/丢包指标

## 为什么控制侧要量化

生产者 100Hz 往 RingBuffer 灌（Day12）。控制循环可能是 50Hz，而且往往只要**最新一帧**。不问「队列里还有几帧」，要问：

- **延迟**：拿到的数据有多旧？
- **丢包**：中间少了多少 seq？有多少是策略覆盖、多少是 bug？

没有数字就无法优化，也写不出 Hub 压测（Week4）。

## 1. 消费频率可以不同于生产频率

```text
生产 100Hz ──覆盖式 RingBuffer──► 控制 50Hz 取最新
```

50Hz 控制循环每 20ms 醒一次，中间大约有 2 帧生产，只取最新则**主动丢 1 帧**。这是设计，要在日志里写成 `policy_drop` 或 seq 间隙，不要和「写 bug 丢了」混成一个数。

```cpp
while (running) {
    auto frame = buffer.pop_latest();  // 或 pop 直到空，留最后一帧
    if (frame) consume(*frame);
    std::this_thread::sleep_until(next_tick);  // 控制周期
}
```

「只要最新」与遥测覆盖策略一致：旧姿态对力矩计算往往不如最新姿态。

## 2. 延迟：`now - frame.timestamp`

```cpp
auto now = clock::now();          // 必须与帧上 ts 同一时钟
auto d = now - frame.ts;
// 累加做均值；样本可放 vector 算分位
```

- **均值**：好懂，会被极端值拉高。
- **P50 / P99**：排序后 50%、99% 处。P99 看尾巴：偶发调度抖、日志、锁。面试能说「看尾部不只看平均」。

样本太少（跑 0.5 秒）分位不准。先跑数秒，每秒打一行汇总，原始样本可不全打。

**队列长度不是延迟。** 长度是积压帧数；延迟是时间差。覆盖式缓冲长度还可能几乎常满或常空，更不能当延迟。

## 3. 丢包：序列号间隙 + 覆盖次数

生产 `seq` 连续 +1。消费若上次 `last_seq=10`、这次 `seq=13`，中间 11、12 没见到，`drop += 2`。

同时 RingBuffer 若提供 `overwrite_count`，那是**缓冲层主动覆盖**。两数关系：

- 控制更慢 → seq 间隙上升，覆盖也可能上升。
- 间隙很大但覆盖为 0：可能是你 pop 逻辑跳过了，或 seq 根本没连续打——要查 bug。
- 只报一个「丢包」分不清策略还是缺陷。

Day09 的「不丢」是任务队列；今天允许丢中间帧，但要**数得清**。

## 4. 输出约定（上机要打出来）

例如每秒一行（方便 `tail -f`）：

```text
t=3.0s consumed=50 mean_us=420 p99_us=1800 gap_drop=48 overwrite=48
```

含义自己在笔记里写清：`gap_drop` 来自 seq，`overwrite` 来自缓冲。两者接近说明主要是策略丢；差很多就要查。

## 5. 易错点（看懂再上机）

1. 帧用 `system_clock`，now 用 `steady_clock`。
2. 把 `q.size()` 当成延迟。
3. 主动丢和 bug 丢一个计数器。
4. 测试 200ms 就报 P99。
5. 每帧 `cout` 还 `endl`，延迟全是 IO。
6. 消费端不用锁/原子就和生产者抢 RingBuffer。

## C++ 面试口述（预习时自己答一遍）

1. **控制循环为什么常常只要最新状态？**  
   力矩/姿态跟当前世界走，过期帧帮不上忙；中间帧可丢，换固定周期和最新数据。

2. **如何报告 P50/P99？**  
   收集一批延迟样本排序，取 50%、99% 位置；样本量和时钟类型要交代。

3. **丢包怎么定义才不混？**  
   seq 间隙 vs 缓冲覆盖次数分开报；策略丢要标明。
